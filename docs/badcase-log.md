# 公众号资源发现与追踪助手 V2 Badcase 与优化复盘记录

> 本文件用于记录后续自然语言反馈的问题、badcase、原因分析、讨论结论、修复方案与验证状态。
> 用户可以直接用口语描述问题；Codex 负责整理、归类、补充复现路径和后续动作。

## 使用规则

- 用户不需要按模板提交问题，可以直接描述现象、困惑、失败路径或不符合预期的地方。
- Codex 每次处理问题时，需要判断这是新 badcase，还是已有问题的补充。
- 每条问题都要记录模块、影响程度、初步分析、讨论结论、后续动作和当前状态。
- 修复完成后，不只写“已修复”，还要补充验证方式和验证结果。
- 如果问题来自 PRD、vibecoding 流程或前端 UI 建议文档的偏离，需要在条目中注明关联依据。

## 状态说明

- `待分析`：已记录，但还没有完成排查。
- `待修复`：原因基本明确，等待实现。
- `修复中`：正在改代码或配置。
- `已修复待验证`：已完成改动，需要实际验证。
- `已关闭`：用户或测试确认问题解决。
- `暂缓`：短期不处理，但保留原因和后续条件。

## 严重程度

- `阻塞`：导致产品主流程无法继续，例如无法访问、无法导入、无法生成资源。
- `严重`：核心体验或数据结果明显错误，但有替代路径。
- `一般`：影响效率、理解成本或局部功能。
- `体验优化`：不会阻断使用，但会造成困惑、割裂或不够顺手。

## Badcase 明细

### BC-001 服务停止后后台无法访问

- 反馈时间：2026-05-13
- 用户原话摘要：访问 `http://127.0.0.1:3001/admin` 时显示“无法访问此站点”，希望 Codex 直接帮忙恢复服务。
- 相关页面/模块：产品前端、本地后端、外部采集工具服务。
- 复现路径：本地服务窗口或后台进程停止后，刷新 `3001/admin`。
- 问题现象：前端站点不可访问，用户不知道下一步该做什么。
- 影响程度：阻塞。
- 初步分析：当前产品依赖多个本地服务同时运行，包括前端、FastAPI、wewe-rss、wechat-article-exporter。服务停止后没有统一入口提示，也没有一键恢复能力。
- 讨论结论：需要保留一键恢复命令，同时后续应在项目中增加更明确的启动脚本、健康检查和失败提示。
- 后续动作：补充统一启动/检查脚本；后台首页展示服务健康状态；README 同步当前端口。
- 当前状态：待修复。
- 后续验证方式：停止服务后重新执行统一启动命令，确认 `3001/admin`、`8001/health`、`4000/dash`、`4100` 都能访问。

### BC-002 无真实文章导入时资源数为 0

- 反馈时间：2026-05-13
- 用户原话摘要：前端生成了，但是资源是 0，完全没有爬取微信公众号文章数据；需要真实能用的产品，而不是空壳。
- 相关页面/模块：搜索首页、管理后台、历史文章导入、数据管线。
- 复现路径：启动产品后，在未完成真实文章导入或同步前查看前台搜索和后台统计。
- 问题现象：产品界面可交互，但没有真实资源数据，搜索结果为空。
- 影响程度：阻塞。
- 初步分析：前台搜索依赖后端 `articles`、`resources` 等数据对象。没有完成 `wechat-article-exporter` 历史冷启动或 `wewe-rss` 增量同步时，资源库为空。
- 讨论结论：P0 必须围绕 PRD 第九章补齐真实数据链路，不能只做空 UI。历史冷启动优先接 `wechat-article-exporter`，增量同步接 `wewe-rss`，文件/链接导入作为补充。
- 后续动作：继续优化导入引导、导入失败提示、真实文章样本验证和搜索结果验证。
- 当前状态：待修复。
- 后续验证方式：导入真实公众号文章后，确认后台文章数、资源数增加，并能在前台搜索到生成的资源卡片。

### BC-003 wechat-article-exporter 批量导出含义不清

- 反馈时间：2026-05-13
- 用户原话摘要：在 `wechat-article-exporter` 中选择了“批量导出”，但没有看到文件下载，不知道导出到了哪里。
- 相关页面/模块：wechat-article-exporter、历史冷启动导入、管理员操作流程。
- 复现路径：打开 `http://127.0.0.1:4100/dashboard/account`，选择批量导出。
- 问题现象：用户以为批量导出会导出历史文章 JSON/HTML，但实际可能是导出公众号账号配置或其他非文章数据。
- 影响程度：严重。
- 初步分析：第三方工具的按钮语义和本产品的“历史文章导入”目标不完全一致。用户在跨工具操作时缺少上下文提示。
- 讨论结论：本产品后台不能只给外部工具链接，需要说明“在哪里导出文章、导出什么格式、导出后怎么导入本系统”。
- 后续动作：在管理后台新增更明确的分步指引；尽量减少用户手动判断第三方工具按钮含义。
- 当前状态：待分析。
- 后续验证方式：用户按后台指引完成一次真实历史文章导出，并成功导入本系统。

### BC-004 内置浏览器下载位置不明显

- 反馈时间：2026-05-13
- 用户原话摘要：选择批量导出后没看见文件下载，不知道文件导出到哪里。
- 相关页面/模块：Codex 内置浏览器、wechat-article-exporter、文件导入。
- 复现路径：在内置浏览器中触发第三方工具文件下载。
- 问题现象：下载完成与否、保存位置、文件名都不清楚，导致导入流程中断。
- 影响程度：严重。
- 初步分析：内置浏览器下载行为不如常规浏览器直观，第三方导出文件可能没有落到用户预期的 Windows 下载目录。
- 讨论结论：产品需要提供替代路径，例如粘贴 JSON/HTML、从固定目录读取、或者让 Codex 辅助查找下载文件。
- 后续动作：优化后台导入页，保留文本粘贴导入；必要时增加“本地文件路径导入”或“最近下载文件提示”。
- 当前状态：待分析。
- 后续验证方式：用真实导出内容通过粘贴或文件方式导入，确认不依赖用户手动找下载位置也能完成闭环。

### BC-005 多服务端口和启动关系缺少清晰状态提示

- 反馈时间：2026-05-13
- 用户原话摘要：现在不知道应该做什么；多个地址包括 `3001`、`8001`、`4000`、`4100`，服务停了以后容易迷路。
- 相关页面/模块：管理后台、本地服务、外部采集工具。
- 复现路径：同时使用产品前端、API、wewe-rss 管理台、wechat-article-exporter 管理台。
- 问题现象：用户难以判断当前哪个服务正常、哪个服务需要登录或配置、哪个服务负责哪一步。
- 影响程度：严重。
- 初步分析：真实数据产品不是单页面应用，而是由产品服务和两个采集工具共同构成。当前缺少统一控制台式的状态解释。
- 讨论结论：管理后台首页需要承担“操作驾驶舱”的角色，展示文章数、资源数、来源数、最近任务，以及外部工具可达状态。
- 后续动作：后台增加服务状态区域；文档更新当前端口；错误时给出下一步动作而不是只显示失败。
- 当前状态：待修复。
- 后续验证方式：打开后台首页即可判断四个服务是否可用，并知道下一步应该导入、同步还是配置。

### BC-007 wewe-rss 增量同步反馈不清且需保证只新增未入库文章

- 反馈时间：2026-05-13
- 用户原话摘要：wewe-rss 同步应该只通知之前没同步过的新文章，包括新公众号文章和同一公众号新文章；不能只是记录决策，必须落实。
- 相关页面/模块：管理后台增量同步、后端导入管线、订阅通知。
- 复现路径：在管理后台点击“增量同步-立即同步”，观察同步结果与通知生成。
- 问题现象：原页面只显示“导入/跳过/资源数”，且成功后会整页刷新，容易吞掉提示；缺少测试保证二次同步不会重复导入旧文章或重复通知。
- 影响程度：严重。
- 初步分析：后端已有按 `article_url` 去重的基础能力，但 UI 没有表达“读取 N 条、新增 X 条、跳过 Y 条”；测试没有锁定“同一 feed 二次同步只跳过、不重复通知”的业务语义。
- 讨论结论：同步可以读取最新一页或多页文章，但本系统只新增以前没入库的文章；通知只应由新文章产生的新资源/新证据触发。
- 后续动作：已更新任务摘要和 wewe-rss 同步完成消息；前端同步按钮现在展示“读取/新增/跳过/资源数”，不再用整页 reload 吞掉提示；已新增单元测试覆盖二次同步跳过和不重复通知。针对 `all.json` 触发 502 的问题，已调整为优先尝试小批量全文 feed；当 HTTP feed 全部失败时，兜底读取本机 `wewe-rss.db` 文章列表，保证增量同步不会直接失败。
- 当前状态：已修复待验证。
- 后续验证方式：用同一个 feed 连续点击两次同步，第二次应显示新增 0、跳过 N，通知数量不重复增加；若 HTTP feed 502，应显示从本地 wewe-rss 数据库完成文章列表同步。

### BC-008 数据库落点变化导致历史数据看似丢失

- 反馈时间：2026-05-13
- 用户原话摘要：昨天导入了两个公众号很多文章，今天重新打开什么都没有了，想知道是否能恢复昨天的数据。
- 相关页面/模块：管理后台、SQLite 数据库、本地启动流程。
- 复现路径：重新打开产品后访问 `http://127.0.0.1:3001/admin`，后台统计只显示少量文章和 0 个资源。
- 问题现象：用户以为昨天导入的数据全部丢失。
- 影响程度：阻塞。
- 初步分析：后端曾允许多个 SQLite 候选路径，包括项目 `data`、`LOCALAPPDATA` 和 Windows 临时目录。实际发现项目库为 12 篇文章、0 个资源，而临时目录大库为 42 篇文章、31 个资源、61 条资源提及。服务切换数据库落点后，历史数据看起来像被清空。
- 讨论结论：以临时目录中的大库作为昨日主数据源恢复到项目固定数据库位置；后端数据库解析逻辑改为只使用项目内 `data/resource_tracker_v2.db`，不可写时直接报错，不再静默 fallback。
- 后续动作：已备份当前小库；已复制昨日大库到项目 `data` 目录；已固定后端数据库路径。需要重启后端并验证后台统计。
- 当前状态：已修复待验证。
- 后续验证方式：打开后台应看到文章数约 42、资源数约 31；重启服务后数据库路径仍为 `D:\AI_project2\wechat-resource-tracker-v2\data\resource_tracker_v2.db`。

### BC-010 仅标题数据无法支撑资源发现，必须获取公众号全文
- 反馈时间：2026-05-13
- 用户原话摘要：用户明确表示“还是要全文，不然这个产品就没意义”，要求重新分析 `wewe-rss` 和 `wechat-article-exporter` 的设计，确认如何稳定拿到公众号全文。
- 相关页面/模块：wewe-rss 增量同步、wechat-article-exporter 历史导出、后端统一文章对象、资源解析、搜索结果。
- 影响程度：阻塞。
- 初步原因：当前从 `wewe-rss` 本地库兜底同步时只能得到文章元数据，包含公众号、标题、链接和发布时间，但没有正文；标题弱识别会把标题短语误当资源名，也无法识别正文里的下载链接、功能描述、证据片段。
- 工具设计分析：`wewe-rss` 的数据库只保存文章元数据，全文模式是在生成 feed 时临时请求 `mp.weixin.qq.com/s/{id}`；`wechat-article-exporter` 则是登录态驱动的批量文章列表、正文抓取、HTML/JSON/Txt/Markdown 导出工具，设计上更适合作为全文冷启动和补全文来源。
- 讨论结论：本产品必须把“全文获取”改成资源解析前置条件。`wewe-rss` 负责发现新文章和增量 URL；`wechat-article-exporter` 负责补齐全文；只有 `full_text` 文章才能进入高置信资源解析和前台搜索。
- 后续动作：新增全文状态字段和后台全文覆盖率；隐藏或禁止标题弱识别资源进入前台；实现从 exporter 导出的 JSON/HTML 或其本地缓存导入全文；wewe-rss 全文 feed 只作为机会性补充，失败时不生成正式资源。
- 当前状态：待修复。
- 后续验证方式：同步 57 篇文章后，后台应显示其中多少篇是 `full_text`；全文为 0 时前台不应产生错误资源；通过 exporter 抓取并导入 BBPlayer 正文后，搜索“免费听歌”必须返回 `BBPlayer`。

### BC-011 wechat-article-exporter 导入 JSON 的 content 为空，导致搜索无结果
- 反馈时间：2026-05-13
- 用户原话摘要：用户导入了一批数据后，无论搜索什么都没有资源。
- 相关页面/模块：管理后台历史导入、wechat-article-exporter 导出、资源解析、搜索页。
- 影响程度：阻塞。
- 排查证据：数据库中已有 12 篇文章和 1 个来源，但所有文章 `content_text` 长度为 0、`content_html` 长度为 0、`content_status=title_only`。原始 JSON 中存在 `content` 字段，但字段值为空字符串。
- 初步原因：这次从 `wechat-article-exporter` 导出的 JSON 是文章列表数据，不是已抓取正文后的全文数据。DeepSeek 没有正文可读，因此无法做结构化资源识别。
- 已落实改动：后端已修改为 `title_only` / `missing_content` 不再生成资源，避免标题弱识别污染前台搜索；导入任务摘要会显示全文数量和标题/缺正文数量；已新增测试锁定“标题-only 不生成资源”规则。
- 当前状态：已修复待重新导入全文。
- 后续验证方式：在 exporter 中先对文章执行“抓取”，确认内容抓取成功，再导出 JSON；重新导入后，后台文章应出现 `full_text`，资源数应由 DeepSeek 解析生成，搜索“免费听歌”应命中真实资源名。

### BC-012 wechat-article-exporter 前端抓取失败但后端全文接口可作为补全文服务

- 反馈时间：2026-05-14
- 用户原话摘要：`wechat-article-exporter` 显示“文章内容抓取完成，本次抓取耗时 3 秒，成功 0，失败 12”，用户希望不要只依赖外部工具手工导出，而是把链接作为前置，系统自己补全文。
- 相关页面/模块：wechat-article-exporter、管理后台全文补抓、统一文章对象、DeepSeek 资源抽取。
- 影响程度：阻塞。
- 排查证据：直接导入的 JSON 里 `content` 为空；但本地 exporter 后端接口 `GET /api/public/v1/download?url=...&format=text` 对部分微信文章链接可以返回正文文本，例如“青听音乐”文章可拿到实际正文。
- 初步原因：exporter 前端批量抓取流程和后端单篇下载接口行为不完全一致；微信链接本身也可能触发 502、风控或短内容返回，因此不能把“有文章链接”直接等同于“已拿到全文”。
- 讨论结论：`wewe-rss` 和 `wechat-article-exporter` 都可以承担“发现链接”的前置角色，但本产品必须内置“链接 -> 全文 -> DeepSeek 结构化抽取”的补全文流程。DeepSeek 不负责点击链接；它只处理已经拿到的正文。
- 已落实改动：新增后端 `POST /admin/articles/fetch-fulltext`，调用 exporter 后端全文接口补抓缺正文文章；新增失败重试；成功补全文后立即进入 DeepSeek 抽取、评分和通知流程；后台新增“补抓缺失全文”按钮。
- 当前状态：已修复待更多链接验证。
- 后续验证方式：导入只有链接和标题的文章后，点击后台“补抓缺失全文”；成功文章应从 `title_only` 变为 `full_text` 并生成真实资源；失败文章应保留明确错误，等待稍后重试或人工粘贴正文。

### BC-013 搜索“免费听歌”误命中只有“免费”标签的非音乐资源

- 反馈时间：2026-05-14
- 用户原话摘要：搜索“免费听歌”时，结果不应返回“蜜蜂记账”这类只有“免费”属性、但不是听歌软件的资源。
- 相关页面/模块：搜索 API、结果排序、能力标签、证据命中。
- 影响程度：严重。
- 初步原因：旧搜索逻辑允许 `tag in query` 的反向包含匹配，导致资源只要有“免费”标签，就能命中“免费听歌”这种复合查询。
- 解决方案：收紧反向包含匹配：`免费`、`安卓`、`软件`、`工具`、`下载` 等泛词不再单独触发复合查询命中；同时增加“听歌/音乐/歌曲/播放器/歌词/无损/音源”的轻量语义域匹配。

- 当前状态：已修复待前台验证。
- 后续验证方式：前台搜索“免费听歌”应优先展示音乐相关资源；搜索“免费”仍可以作为宽泛查询找到免费资源，但不会污染复合需求。
